## The event loop

The C SDK operates on an event loop, but you control when the events happen. 

All state changes and all callbacks happen synchronously on the thread that you call `ngp_sdk_run_callbacks`. This provides a few useful properties:
- Predictable native SDK callback patterns - you decide when we call back into your code.
- Interacting with the SDK and calling `ngp_sdk_run_callbacks` from the same thread eliminates multithreading concerns for you.
- You can use `ngp_sdk_run_callbacks` as a sync point when you do access data from other threads.

### Callbacks and events

Many of the APIs in the C SDK are asynchronous, and present this constraint in the form of callbacks.

The async callback convention we follow includes:
- Async callbacks always have a `ngp_result` if it is fallible. The C SDK assumes you check `result.ok` is `true` before using the data.
- We return a single object that contains all relevant info to the callback rather than multiple parameters.
    - If applicable, the context object is always one of these parameterse.
- We also take a `void* user_data`.

The C SDK use the `void* user_data` pattern to enable you to associate arbitrary data with a callback. The SDK doesn't do anything with this except copy it into the callback when it is called, so you can use it to correlate callbacks within your own codebase. The C++ API makes heavy use of these for this exact purpose.

Events often have context objects like any other function. You need to make sure you call the removal function before the context object is destroyed. Any context objects that can be destroyed have a related event that always fire just before they are freed.

For example, controllers have `ngp_sdk_add_controller_removed_callback`. During this callback, you should unbind any events bound to that controller. After the callback it will be freed.

#### Memory management

The only memory you need to worry about from the C SDK is the `ngp_sdk` object itself. The SDK assumes you will destroy the object created by `ngp_sdk_create` with `ngp_sdk_destroy`. Every other pointer you received, including C strings, is freed at an appropriate time within the SDK.

##### Synchronous return values as pointers or with pointers
For context objects like `ngp_sdk` or `ngp_controller`, the lifetime of all pointers to the object are the same, and are freed immediately following a relevant remove/destroyed event. For example, `ngp_controller*` returned from `ngp_sdk_get_controller_at` is valid until the `controller_removed` for that pointer fires.

For data pointers, such as `const char*` return from a function, the pointer is guaranteed valid until the next call to `ngp_sdk_run_callbacks` unless otherwise specified. Therefore, he data model of the SDK runtime is also bound to `ngp_sdk_run_callbacks`. You should use it immediately and/or explicitly copy any data you want to cache.

##### Async callbacks and events
Any non-context-object data passed to these callbacks is freed after the function is called. The C SDK assumes you explicitly copy any data (such as C strings) that you want to keep outside of the callback scope.


## Feature APIs

Once you Get started with the C SDK, you can integrate all the different features of the SDK into your game. All of these features build on the base APIs of the SDK, Company account, and specific player profile.

>*Sara note: May move the base API table information into the larger table as part of each feature's description. "X builds from the SDK" or "Y builds from the player profile"*

| What you want to do | The base API you need |
| --- | --- |
| Add a controller callback<br/>Run callbacks<br/>Fetch sessions or telemetry | The SDK (`ngp_sdk*`) |
| Listen for profile-switch events | Company account (`ngp_account*`) |
| Read/write achievements, leaderboards, stats, blobs (cloud saves)<br/>Render the player name<br/>Pick language | Player profile (`ngp_player*`) |

Depending on the game you are building, you may or may not use all available features.
